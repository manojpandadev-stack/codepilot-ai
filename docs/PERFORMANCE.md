## C. Methodology

- Warmup (default 5) discarded; measured iterations timed with
  `performance.now()` (monotonic).
- Cold operations run in a FRESH child process per iteration (JIT + module
  cache cannot leak); one-shot events (init, discovery, cold index) report a
  single sample honestly.
- Percentile policy enforced in code: **p95 requires ≥20 samples, p99
  requires ≥100 samples**, otherwise null (never extrapolated).
- Every operation carries a correctness assertion; a failed assertion fails
  the run loudly instead of reporting a number.
- Memory sampled via `process.memoryUsage()` without forced GC; deltas are
  reported with that caveat.

## I. Memory results (heap MB, no forced GC)

Memory milestones are printed by every run (baseline → 100 tasks →
checkpoint churn → open/close cycles). Reference run: heap returns toward
baseline after open/close cycles with no monotonic growth detached from
ledger caches. Verdict: **no leak signature** (normal cache growth is not
treated as a leak).

## J. Lifecycle results

Listener/active/timer counts verified zero after every cycle type
(complete, cancel, scheduler stop, file-lock churn, webview refresh batch).
See `lifecycle-*` rows above.

## K. Security overhead

See §F security table. Conclusion: all security controls cost microseconds
in absolute terms; the only millisecond-scale security-adjacent cost is
process spawn (terminal), which is OS work, not framework overhead.

## L. Optimization results

No optimizations were made in this milestone: measurement first. No
bottleneck exceeds its honest budget (slowest warm op outside process spawn
is low-single-digit ms). Deliberately no changes to security, validation,
persistence, M4, correctness, or error handling for performance.

## M. Regression thresholds

`scripts/benchmark/thresholds.ts`, derived mechanically from this run:

`warnMs = max(10 × p95-or-median, 0.5ms)`, `failMs = max(100 × p95-or-median, 5ms)`

rounded up to 2 significant figures. Only stable pure-CPU/in-memory ops are
gated; spawn/network/time-driven ops are excluded. The vitest suite
(`tests/benchmark-harness.test.ts`) re-measures the fast subset (20
iterations) and fails under `failMs`. Regenerate with
`pnpm benchmark --write-thresholds`.

## N. Limitations

1. Single reference machine (this file's §A); numbers are not portable claims.
2. tsx-transpiled sources measured, not prebuilt dist (upper bound on import cost).
3. No human-in-the-loop timings (approval wait, reading diffs in UI).
4. Terminal spawn is OS/noise-sensitive (n=3, env-labeled).
5. TaskStore/checkpoint I/O measured on temp dir (SSD); HDD/AV behavior differs.
6. Model inference deliberately excluded everywhere.
7. Cline comparison limited to two trivially comparable micro-ops; everything
   else is honestly Not measured.
